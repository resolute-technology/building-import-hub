## Architecture verdict

**Static Firebase Hosting is technically correct after these local fixes.** `.output/public/_shell.html` is the only generated public HTML file. Its module scripts, preloads, CSS, and icon resolve to generated public assets. Firebase deploys `.output/public` and rewrites unmatched requests to `/_shell.html`. There is no function/run rewrite and no Firebase App Hosting requirement.

**No application frontend feature depends on a TanStack server runtime.** Router loaders and Auth run in the browser, buildings query Supabase directly, and the upload invokes `supabase.functions.invoke("import-buildings")`. `src/lib/buildings.functions.ts` was absent from this checkout; its stale import was already being replaced in the user's deployment changes. No active `createServerFn` references remain in application source. Removed `auth-attacher.ts`, `client.server.ts`, and `cron-auth.ts` only after a repository reference search found no callers.

Nitro/server output is still generated by the existing Lovable wrapper, and generic TanStack server-function transport code/`/_serverFn/` strings can remain in bundled framework code. Neither proves an application RPC dependency. The Hosting emulator and Chrome checks used the static public directory with no TanStack server running. `src/server.ts` and build error helpers remain for wrapper/build compatibility.

**Supabase is ready for runtime verification, not certified production-ready.** Current local public URL matches the requested project and the public key has a publishable prefix. No credential values were printed in this report. Browser sessions are configured to persist and refresh, and Lovable preview storage remains available. Real login/refresh persistence was not exercised. The migration defines the expected table, user index, grants, RLS enablement, and per-user policies. UPDATE's existing `USING` policy also supplies its implicit `WITH CHECK`; ownership-changing updates must be verified remotely. No schema migration changes were necessary.

The Edge Function uses a public API key and forwards the caller's bearer JWT, verifies it online with Auth before parsing or inserting, and sets ownership from the verified user. `verify_jwt = false` leaves application-level JWT validation responsible for access control; that check remains mandatory. CORS supports POST/OPTIONS and explicit bearer credentials from live, preview, and Lovable origins; wildcard origins do not grant access without a user token. Deno imports and type declarations were checked using Deno 2. No service-role client is used. Static output passed a scan for secret API-key patterns and service-role JWTs; this is a targeted scan, not a comprehensive secret-discovery proof.

**GitHub Actions is correctly configured locally.** Both workflows install with `npm ci`, select Node 24, run lint/tests/build/static checks, inject the public `VITE_*` values, and use the intended Firebase project. The action reads `firebase.json` for `.output/public`. Same-repository PRs get preview channels; fork PR deployment is intentionally skipped. Production runs on pushes to `main`, with source-read permission only; previews also need check/comment permissions. Actual workflow execution and repository settings were not inspected.
